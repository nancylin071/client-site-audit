How it works

三層怎麼用

按需載入：每案只執行 ① 主 Prompt；僅在平台判定為「低／未能確認」時，才將 ② Reference 提供給 AI；③ 團隊 SOP 僅供同仁閱讀，不提供給 AI。

① 主 Prompt每案皆須執行。讓 Claude 讀取官網並產出快速健診報告。
② 平台 Reference僅在主 Prompt 對平台判定信心低時載入。
③ 團隊 SOP供同仁閱讀的操作說明，不提供給 AI。
①Main Prompt · 每案執行

主 Prompt

複製完整內容，貼給具備瀏覽能力的 Claude（Claude in Chrome 或可操作瀏覽器的 Agent）。

quick-audit.prompt 
你是將能數位行銷的資深 SEO／GEO 顧問。

請實際使用瀏覽器工具讀取目前開啟的客戶官網；若目前沒有網站分頁，請使用我提供的網址進行檢查。

這是提案前的快速健診，沒有客戶 GA4、Google Search Console 或網站後台權限，只能依第三方工具與瀏覽器可實際觀察到的資訊判斷。

【請實際檢查】

1. 目前頁面的原始 HTML 與 head：
title、meta description、meta robots、canonical、hreflang、viewport、Open Graph、JSON-LD。

2. 網站基礎檔案：
/robots.txt
/sitemap.xml 或 /sitemap_index.xml
/llms.txt（若有）

3. 頁面載入的 script、CSS、圖片資產網域與其他可觀察技術線索，用來辨識架站平台與追蹤／行銷工具。

4. 原始 HTML 與 JavaScript 渲染後頁面的差異，確認主要內容與連結是否高度依賴 JS。

5. 頁面內容結構：
H1／H2、主要文字內容、圖片 ALT、FAQ、結構化資料，以及頁面是否能清楚說明主題。

【判斷規則】

1. 只報告實際讀取或觀察到的內容，不得臆測；無法確認就直接說明。

2. 清楚區分「已確認」與「推測」。所有重要結論都需附上實際辨識依據。

3. 單頁只能反映目前檢查頁面的狀況，不得直接推論全站皆相同。

4. 架站平台需綜合 script／CSS／圖片資產網域、原始碼、頁尾、網址結構等證據判斷，不可只憑單一字串。

5. 平台判斷需標示：
平台｜信心度（高／中／低／未能確認）｜辨識依據

6. 若平台信心為「低／未能確認」：
- 不得直接判定為客製化網站
- 優先確認是否為台灣在地 SaaS／電商平台
- 可搭配平台辨識 Reference、Wappalyzer、WhatCMS 或公開資料覆核
- 未確認平台前，不得自行判定技術 SEO 可控性高低

7. 技術可控性需區分「平台通常具備的能力」與「目前實際能否修改」。後者若沒有後台或方案資訊，只能標示需向客戶／平台確認。

8. llms.txt 可記錄是否存在，但目前不是 SEO／GEO 必備項目，沒有 llms.txt 不得直接列為缺失。

9. 檢查 robots.txt 中與搜尋引擎及 AI 服務相關的存取規則時，需依各 crawler 的實際用途分開說明，不得把「AI 搜尋內容存取」與「模型訓練資料使用」混為一談，也不得將封鎖訓練型 crawler 直接視為 GEO 缺失。

10. 偵測到 GA4、GTM、Meta Pixel、Google Ads、LINE、TikTok 等工具，只能表示網站存在相關追蹤／行銷技術，不代表目前一定正在執行該行銷活動。

【輸出格式】

■ 受檢資訊
網址、檢查範圍，以及本次實際讀取到的頁面／檔案。

■ 1. 架站平台與技術修改限制
平台、信心度、辨識依據。
說明目前可合理判斷的技術 SEO 可控性，以及可能受平台／開發資源限制的項目。
無法確認的部分直接標示需人工覆核。

■ 2. SEO／GEO 基礎建置訊號
整理目前頁面已具備與缺少的 SEO／AI 理解基礎，例如：
Title／Meta、標題結構、canonical、hreflang、結構化資料、FAQ、文字資訊完整度等。

僅描述可觀察到的建置狀況，不直接判定實際 SEO／GEO 成效。

■ 3. 搜尋引擎與 AI 內容存取風險
列出真正可能影響搜尋引擎或 AI 取得、理解內容的問題。

每項以：
問題｜依據｜可能影響｜嚴重度

呈現。

優先檢查：
robots.txt、meta robots、canonical、Sitemap、JS 渲染、結構化資料、H1／H2、重要資訊圖片化、多語 hreflang，以及 AI 相關存取規則。

■ 4. 追蹤與行銷工具配置
列出實際偵測到的分析、廣告、社群、再行銷或其他追蹤工具。
只描述已偵測到的技術，不反推目前實際行銷活動。

■ 5. 需進一步補查的項目
先說明本次無法確認的項目，再列出建議工具：

自然搜尋與關鍵字：Ahrefs
Google 搜尋收錄線索：site: 查詢
實際索引狀況：Google Search Console（取得權限後）
速度與 Core Web Vitals：PageSpeed Insights
全站 404、轉址、重複內容等：Screaming Frog

文字需精簡、自然、讓非 SEO 背景的客戶也能理解，可直接作為提案前分析素材。

platform-reference.md 
# 台灣常見架站平台辨識 Reference

用途：
當網站架站平台無法明確辨識時，協助判斷台灣常見 SaaS／電商平台，避免把模板型 SaaS 誤判為客製化網站。

【判斷原則】

1. 優先看 script、CSS、圖片等「資產網域主機」。
2. 頁尾、URL 格式、原始碼字串、結帳網址只能作為輔助證據。
3. 單一關鍵字不可作為平台確認依據。
4. 找不到 CMS 指紋不代表客製化。
5. 低信心平台需搭配官方資料、WhatCMS、Wappalyzer 或人工確認。
6. 平台辨識與「客戶實際可修改哪些 SEO 項目」是兩件事；後者仍可能受到方案、權限與客製程度影響。

【主流平台】

WordPress
強指紋：wp-content、wp-includes、wp-json、generator=WordPress
一般特性：開源、整體可控性較高，但仍受主題／外掛／開發方式影響。

Shopify
強指紋：cdn.shopify.com、myshopify.com、/cdn/shop/
輔助：/products/、/collections/、Powered by Shopify
一般特性：SaaS，部分 URL 與模板架構固定，深度調整可能需 Liquid／App。

Wix
強指紋：wixstatic.com、parastorage.com
一般特性：SaaS，部分伺服器與底層技術設定受平台限制。

OpenCart
強／中強線索：index.php?route=、catalog/view/
輔助：Powered By OpenCart
一般特性：開源，可控性取決於模板與開發資源。

【台灣／亞洲 SaaS】

SHOPLINE
強指紋：
cdn.shoplineapp.com
img.shoplineapp.com
shoplineimg.com
shoplytics.com
myshopline.com

輔助：頁尾 SHOPLINE 技術支援字樣。

技術判斷：
視為模板型 SaaS；Title／Meta、結構化資料、URL 等實際可調範圍依平台功能與方案確認。

91APP
強指紋：
*.91app.com
例如 tracking-client.91app.com、cdn.91app.com、img.91app.com

輔助：官方 APP／相關頁面線索。

技術判斷：
常見 SPA／App 化架構，需特別確認原始 HTML 與 JS 渲染後內容差異。

CYBERBIZ
線索：cyberbiz.io 等相關平台網域。
信心不足時需覆核。

meepShop
線索：meepshop、meepcloud 等平台網域。
部分網站可能採一頁式商店架構，需依實際網站確認。

【低信心台灣 SaaS】

以下平台不宜只靠單一字串確認：
QDM
WACA
JOO
BV SHOP
FreeStore

若懷疑屬上述平台：
- 查頁尾技術支援文字
- 查 script／CSS／圖片資產主機
- 查看購物車／結帳流程網址
- 查看 robots.txt／sitemap 格式
- 使用 WhatCMS／其他工具或公開資料覆核

在確認前：
不得標示為客製化網站，也不得直接判定技術可控性高。

JOO：
若確認為 JOO，index.php?action= 等動態參數可能與平台架構有關，不應直接寫成「客戶網站技術錯誤」。

FreeStore／一頁式商店：
若確認網站本身就是一頁式架構，分類階層、麵包屑等一般電商檢查項目可能不適用。

M2 微商城：
若實際屬 LINE／LIFF 等微商城生態，需先確認是否具備可正常由搜尋引擎索引的獨立公開網站，再決定哪些 SEO 健診項目適用。

【其他架構】

SAP Commerce Cloud／Spartacus
spartacus、SAP 等為重要線索，但需搭配其他證據確認。
常見企業級 SPA；需檢查 JS 渲染與原始 HTML。

Next.js
__next、Next.js 相關資產只能證明前端框架，不代表網站一定為「純客製化」。
仍需另外判斷 CMS／Commerce／Headless 後端。

客製化網站
只有在合理排除 CMS、SaaS、Headless Commerce 等可能後，才能標示為「推測客製化」。
技術可控性不得自動寫成高，實際仍取決於原始架構與開發資源。
③SOP · 給同仁看，不進 AI

團隊使用 SOP

適用工具：具備網站瀏覽能力的 Claude（Claude in Chrome、可操作瀏覽器的 Agent／Cowork）。不需限定 Chrome 外掛。

  1. Step 1　開啟客戶官網並提供網址。建議一次提供「首頁＋一個產品／服務頁＋一個內容／文章頁」——只看首頁不足以代表全站；各頁分別執行或一次帶入，最後綜合。
  2. Step 2　執行「客戶網站 SEO／GEO 快速健診」主 Prompt。
  3. Step 3　先看架站平台信心度。高／中證據合理可續用報告；低／未能確認不要直接採用平台與技術限制結論，進 Step 4。
  4. Step 4　用「台灣常見架站平台辨識 Reference」進一步判斷。必要時搭配 Wappalyzer、WhatCMS、人工查看原始碼／資產網域／頁尾／結帳網址。仍無法確認就保留「未能確認」，不要硬判。
  5. Step 5　檢查報告裡所有「需進一步補查」項目。依需求用 Ahrefs（自然搜尋／關鍵字／頁面）、PageSpeed Insights（速度／CWV）、Screaming Frog（全站技術）、site:（收錄線索）。
  6. Step 6　挑真正適合提案的問題，不要把整份報告直接搬上簡報。快速健診的目的是「找出值得進一步確認與提案切入的問題」，不是在沒有後台與完整爬站資料下替網站下完整技術診斷。

進階使用

  • 特定內頁：切到產品頁、服務頁或文章頁後重新執行，可比較不同頁型。
  • 競業：分別對競業執行同一 Prompt，再挑真正有差異的項目比較。
  • 平台辨識：團隊未來驗證出新的台灣平台指紋，只更新 Reference，不需要改主 Prompt。
